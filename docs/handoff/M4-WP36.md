One launch path: double-tap "Open app" runs through `HomeGesturesController.executeGestureAction` → `HomeSlotsController.launchApp`; the quiet list wraps `listener.open` in the focus check plus `BadHabitDialogs.gateLaunch` and counts the open; website slots/folders, omnibox web search, "!bang", the no-results search and both search gestures go through `BadHabitDialogs.gateWebOpen`.
Contract: an app launch (anything ending in `startMainActivity`) is `gateLaunch` → `MainViewModel.selectedApp`; a web open is not an app launch and is gated only on its resolved handler — `WebLaunchTarget.gatedPackage(handler)` returns "" for no handler or the chooser ("android"), so nothing is gated then and `MainViewModel.launchUrl` still pins a whitelisted browser under focus; the focus toast is `FocusModeManager.showBlocked(context)` everywhere; `DoubleTapActionManager` is storage only (`execute` is gone).
Not verified: any route on a device (focus + limit + pause sheets from double-tap, the quiet list and the omnibox); whether a snoozed notification's `contentIntent` still opens after the pause's coroutine delay; open counts for web opens are not recorded (the browser is not "opened" as an app) and quiet-list opens count only for the personal profile.
Easy to get wrong: `gateWebOpen` does its own focus check because `gateLaunch` passes focus-blocked packages straight to `open()` expecting it to toast; `gateLaunch` with packageName "" opens immediately, which is the intended chooser/no-handler case, not a bug; `executeGestureAction` must keep handling `QUIET_LIST` for imported double-tap values.

Quiet notifications release instead of cancelling: allowing an app or turning the filter off re-snoozes Parem's keys for 1 ms so they return to the shade at once, and opening or dismissing a quiet-list item only marks it.
Contract: `helper/notifications/QuietKeys` holds the decisions with JVM tests (posted action: pass-through > dismissed-unchanged cancel > filter, a mark counting only within its key's snooze window; list visibility; prune; releasable keys; legacy decode); `quiet_keys` entries are `snoozed:<key>` → snooze time and `dismissed:<key>` → `Notification.when`, and the old `SNOOZED_KEYS` set migrates as snoozed now; `QuietNotificationsManager.setAllowed` releases newly allowed packages and `turnOff(context)` releases before unbinding.
Settles M4-WP1's open points from AOSP android16 source, not a device: a listener's cancel on a snoozed key is a no-op; a post on a snoozed key is merged into it and reaches neither shade nor listener; the expiry repost alerts before listeners see it; snoozes survive a reboot, but `getSnoozedNotifications` lists a key only after its app reposts.
Not verified: any device, so the 1 ms release, the expiry cancel of a dismissed item and the reboot prune rest on reading AOSP; a key the system still holds after a reboot, before its app reposts, cannot be released, so turning off leaves it until its snooze ends.
Easy to get wrong: never cancel or forget a key that is still snoozed, or that conversation goes silent until expiry; the in-memory pass-through entry must exist before the release snooze, or a repost that lands while still bound is snoozed again.

The widget bind/configure/rebind step in flight is saved state (`MainActivity.pendingWidgetOp`, a Bundle in savedInstanceState) instead of a lambda, so a rotation or process death under the system dialog still adds, restores or cleanly cancels the widget; invalidated widgets stay in `WIDGET_IDS` until their rebind completes or is refused, and `restoreWidgets()` deletes host IDs nothing refers to.
Contract: `MainActivity` owns `pendingWidgetOp`/`pendingWidgetResult` and routes every bind/configure result to `HomeFragment.widgetController.onPendingWidgetResult(success)`; `helper/WidgetIdBookkeeping` (idsToKeep, replaceId, orphanIds) is the pure rule set for trap #2, with a JVM test.
Not verified: Before integration, no device run — rotate during bind/configure/rebind, process death under the dialog, and work-profile configure (`onActivityResult` path) are checks for the device pass.
Easy to get wrong: `WIDGET_IDS` may now hold IDs the host no longer knows (provider saved, rebind pending); any code that rewrites the list must keep them (`WidgetIdBookkeeping.idsToKeep`), and the orphan sweep must always exclude the pending op's ID or it deletes the widget mid-bind.
Easy to get wrong: a result that lands while `restoreWidgets()` is suspended is parked in `pendingWidgetResult` and taken after the list rewrite; handling it inline would let the restore overwrite the rebound ID.
Contract: pending operation and deferred result are restored before fragment inflation; result launchers register before a restored bind can advance to configuration, and an empty widget list still drains deferred results.
Verified: ADB on Nothing A069 / Android 16, separate com.parem.launcher.qa build: Analog clock bind/configure completed and widget ID/provider survived force-stop/relaunch; am kill was attempted during external dialogs but actual process death was not confirmed.

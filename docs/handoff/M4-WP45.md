Settings card 1 has an explicit "Hidden apps" row (hiddenAppsRow / hiddenAppsCount, WP35 semantics via bindValueRow) whose count is the installed hidden apps from viewModel.hiddenApps; it and the legacy title tap both open the FLAG_HIDDEN_APPS drawer; hiding from the app menu stays in place and toasts hidden_apps_message; the launch drawer's empty result shows hidden_apps_hint when the query matches a hidden label and opens the hidden list on tap.
Contract: helper/HiddenAppHint.show(query, visibleRows, privateSpaceLocked, hiddenLabels) is the whole gating decision (blank query, any visible row, a locked Private Space, or no SearchMatcher hit on a hidden label all mean no hint); SettingsSearchIndex anchors hidden_apps on hiddenAppsCount; the MainActivity HIDDEN dialog branch is gone and nothing posts Constants.Dialog.HIDDEN any more (the constant still exists, unused).
Not verified: nothing on a device; the hint tap navigates by destination id (R.id.appListFragment) with no nav action, so its transition is the default; the count's first paint is prefs.hiddenApps.size and is corrected by the observer, so an uninstalled-but-still-hidden package can show a higher number for a frame.
Easy to get wrong: AppListSource.isPrivateSpaceLocked() is true when there is no private profile at all, so the drawer uses its own privateProfile + quiet-mode check (no profile = not locked), otherwise the hint would never show on phones without Private Space; the launch drawer requests getHiddenApps() only when prefs.hiddenApps is non-empty, and the app-menu onChanged refreshes it after a hide. Late hidden-label loads refresh the empty-result hint; stale filter callbacks cannot overwrite the current query tip.
Scope: hidden_apps_message was reworded into the hide confirmation and its 18 stale translations deleted; the onboarding search guide now points at the Settings row; AppMenu.kt (not on the roadmap file list, where the hide path lives since WP53) got the one-line toast.

The app is edge-to-edge on API 29-36 with real insets: `MainActivity` sets `WindowCompat.setDecorFitsSystemWindows(window, false)` (no more `FLAG_LAYOUT_NO_LIMITS` or `windowTranslucent*`), and home, drawer (plus `ime()`), Settings, onboarding and `BottomSheetMenu` pad by `systemBars() or displayCutout()` through `View.padForSystemBars()` in `helper/Extensions.kt`; the manifest opts into `enableOnBackInvokedCallback` and the activity's Back callback is enabled only on `mainFragment`.
Contract: `View.padForSystemBars(ime)` adds insets on top of the padding present when it is called, so layout padding is the design spacing (home 24/16dp, drawer 56/148dp, settings 32dp, land 24/8/64/24dp) and nothing else may call `setPadding` on those roots; off home, Back is handled by `NavHostFragment` and the onboarding callback, never by `MainActivity`.
Not verified: no device run — the inset spacing on gesture vs 3-button nav, the cutout overlay, the keyboard-above-results behaviour, whether MDC's `BottomSheetDialog` window is edge-to-edge on API 35+ (if it is not, the sheet listener sees a zero inset and is harmless; double bottom padding would mean it both fits and delivers insets), and the peek itself.
Not verified: the nav graph still uses `@anim` resources; FragmentManager seeks only Animators/Transitions, so seekable drawer and Settings transitions remain incomplete until M4-WP55 supplies animators.
Easy to get wrong: `HomeSlotsController` measures `dateTimeLayout.top` relative to the padded root, so slot fitting is inset-independent, but its clock-hidden fallback (56dp) now sits below the status-bar inset as well; hiding the status bar re-dispatches insets a frame after `onResume`, so a capacity change from that toggle shows on the next resume.
Contract: Settings and home both toggle status bars through WindowInsetsControllerCompat, preserving edge-to-edge flags on API 29.

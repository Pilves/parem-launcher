Adding a widget respects home-app capacity: `HomeWidgetController.bindWidget` refuses a new (not swapped) widget whose default height (200dp plus the first widget's 8dp scroll margin) exceeds the room the last fitting pass measured under the configured rows, with a toast naming the app count; the fitting pass in `HomeSlotsController` names any apps it still hides (Snackbar, once per change of that set), and the app column re-fits whenever its height changes, which is how a late or changed system-bar inset (status-bar toggle, nav mode) reaches it.
Contract: `helper/HomeCapacity` (fitting, hiddenLabels, room) is the arithmetic with a JVM test; `HomeSlotsController.widgetRoomPx` (null until measured; negative means real overflow) and `widgetsShareColumn` (false in landscape, where widgets have their own column) are what the widget flow reads; strings `widget_doesnt_fit` and `home_apps_hidden`; widget ID storage is untouched.
Not verified: no device run — the refusal threshold against a real first widget, the Snackbar after a drag-resize that hides a row, a rotation with hidden rows, and whether the inset-driven re-fit fires on a status-bar toggle without a resume.
Easy to get wrong: the room check uses the measurement from the last fitting pass, so it is only as fresh as the last `populateHomeScreen`; the hidden-apps message re-announces once per HomeFragment view (rotation included) while the condition persists, by design, and only names occupied slots.
Easy to get wrong: the re-fit listener keys on the column's height, not its padding; widget scroll margins count against capacity and completing a drag-resize triggers re-fitting; the fitting pass changes padding and row visibility, neither of which changes a match_parent column's height, so it does not loop.

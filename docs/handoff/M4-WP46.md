Settings has an "Open single match automatically" row (Home screen section, default on, Prefs `autoLaunchSingleMatch`, a plain exported boolean) that turns off single-match auto-launch; auto-launch is also off while touch exploration or a spoken-feedback accessibility service is on.
Contract: `OmniboxResolver.autoLaunchAllowed(query, enabled, screenReaderOn)` = enabled && !screenReaderOn && !blocksAutoLaunch(query), called from AppDrawerFragment's `autoLaunchGuard` lambda; the adapter is unchanged by this row and still ANDs WP27's `blocksAutoLaunch(query)` itself. No commit beat (owner decision 5).
The row is the first with DESIGN 6.3 semantics: `autoLaunchRow` is the click target and screenReaderFocusable with `ViewCompat.setStateDescription`, its label and value are `importantForAccessibility="no"`; the index anchors on the row id.
Not verified: with TalkBack on the Tab S8, that typing "m" with one match leaves the drawer open and that the row reads "Open single match automatically, On"; appended to the UX device pass.
Easy to get wrong: the screen-reader state is read when the filter publishes, not cached, so toggling TalkBack mid-session needs no listener; the setting is read from Prefs on every publish for the same reason.

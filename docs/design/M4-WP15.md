# M4-WP15: Omnibox quick actions (design proposal)

Status: proposal, revised after review. Awaiting sign-off: the "remind me" deviation and the Estonian keywords
(see "For DECISIONS.md"). Base: `origin/next`.

## Problem

"alarm 7:30", "timer 10m" and "event friday 3pm dentist" should work from drawer search with no new permission,
and an app search must never turn into an action.

**Alarm and timer**
([AlarmClock](https://developer.android.com/reference/android/provider/AlarmClock),
[permission](https://developer.android.com/reference/android/Manifest.permission#SET_ALARM))
- `ACTION_SET_ALARM`/`ACTION_SET_TIMER` need `com.android.alarm.permission.SET_ALARM`, protection level **normal**.
- The manifest **already declares it**, so no permission is added and Data safety does not change. Its comment
  (`Used only for opening alarm app`) becomes false and is rewritten in the same PR (see Exact scope).
- Alarm extras are `EXTRA_HOUR`, `EXTRA_MINUTES`, `EXTRA_MESSAGE` and `EXTRA_SKIP_UI`. The alarm rings at the next
  occurrence of that time. There is no date extra.
- The timer takes `EXTRA_LENGTH` in seconds, **1..86400**.

**Calendar**
([provider guide](https://developer.android.com/guide/topics/providers/calendar-provider#intents),
[common intents](https://developer.android.com/guide/components/intents-common#AddEvent))
- `ACTION_INSERT` on `Events.CONTENT_URI`, with `EXTRA_EVENT_BEGIN_TIME`/`END_TIME` (epoch ms), `EXTRA_EVENT_ALL_DAY`
  and `Events.TITLE`.
- "Your application doesn't need permissions"; the user saves in the calendar's editor. No reminder row (needs
  `WRITE_CALENDAR`).

**Package visibility**
([docs](https://developer.android.com/training/package-visibility/automatic))
- An implicit `startActivity` needs no `<queries>`. Catch `ActivityNotFoundException`.

## Options

| | What | Cost | Tradeoffs |
|---|---|---|---|
| A. Keyword-first parser | Fixed en/et keyword, and the whole query must parse | ~250 LOC + tests | Can't misfire; keywords to learn |
| B. Free-form ("dentist fri 3pm") | A time anywhere in the query | 2–3× the code | Collides with app and contact names |
| C. "remind me" → calendar | What the roadmap says | same as A | Fires only if the calendar's default notification is on |

## Recommendation

**A.** I'm deviating from the roadmap on one point and Patric needs to confirm it:
- "remind me" with a time only becomes an **alarm with a label**, because an alarm actually rings.
- "remind me" with a day becomes a calendar event.

**Grammar.** Case-insensitive, whitespace collapsed, and the whole query must match.

| Action | Pattern | Result |
|---|---|---|
| Alarm | `alarm\|äratus <time> [label]` | alarm at that time |
| Timer | `timer\|taimer <duration> [label]` | timer of that length |
| Event | `event\|sündmus\|kohtumine [day] [time] <title>` | needs a day or a time. No time = all-day. Time only = today, or tomorrow if past. Lasts 1 h |
| Reminder | `remind me\|tuleta meelde [day] <time> <text>` | no day = alarm with `EXTRA_MESSAGE`. With a day = event |

**Tokens**

| Token | Accepted | Rules |
|---|---|---|
| `<time>` | `7:30`, `7.30`, `19:30`, `7am`, `7 pm`, `at 7`, `kell 7` | A bare hour only after `at`/`kell`. `pm` needed for evening; the locale is not used to guess |
| `<duration>` | `10m`, `10 min`, `1h30m`, `90s`, `2 hours`, `5 minutit`, `1 tund`, `30 sek` | Unit required. Total 1..86400 s |
| `[day]` | `today`, `tomorrow`, `täna`, `homme`, full weekday names (en and et) | A weekday means the next one, so today's weekday means next week. No numeric dates (`3.10` is a time) and no et letter abbreviations |

**Precedence in `OmniboxResolver`:** calc → conversion → currency → dial → web → **quick action** → contact.
- Disjoint from calc/dial/currency; web's leading space is explicit intent; a contact "Timer" must not take "timer 10m".

**Auto-launch while typing an action (suppressed)**

The drawer launches the only matching app by itself (`AppDrawerAdapter.autoLaunch`, gated by
`autoLaunchGuard = { !isSearchComposing() }`). With `SearchMatcher` as it is on `origin/next`:
- "Alarmy" matches `ala`, `alar`, `alarm` and `alarm ` (raw `contains`). It stops matching at the first digit:
  `alarm 7` normalizes to `alarm7`, and the token rule needs a second label word.
- "Multi Timer" matches `timer` and `timer `. It stops at `timer 1`.
- Two-word labels keep matching past the space: "Remind Me" matches `remind me`, and "Timer Plus" matches `timer p`.

So the risk window opens **before** the space, not at it. Guarding only "keyword + space" would still launch Alarmy
at `alarm`. The rule is:
- **Suppress auto-launch** while the query, without a leading space and with whitespace collapsed, is either
  - a prefix of at least 3 characters of `keyword + " "` (for example `ala`, `alarm`, `alarm `, `remind m`), or
  - starts with `keyword + " "` (for example `alarm 7`, `timer p`, `remind me 5pm`).
- This is implemented as `QuickActionParser.isActionPrefix(query): Boolean`, and
  `autoLaunchGuard = { !isSearchComposing() && !QuickActionParser.isActionPrefix(currentQuery) }`.
- The guard reads the search field's current text when the filter callback runs. Fast typing therefore makes it
  more conservative, never less.
- Enter still works. If the query does not parse, submit falls through to `launchFirstInList()`, so someone who
  really wants Alarmy types `alarm` and presses Enter, or types `alarmy`, which auto-launches as before.
- **Cost:** an app whose unique prefix is one of these strings needs one more letter or Enter. For example, `eve`
  no longer auto-launches Evernote, but `ever` does. Prefixes of 1 or 2 characters are left alone, because unique
  2-letter shortcuts are what auto-launch users rely on. Typing `al` when only Alarmy matches still launches it.
  That behaviour already exists today and I accept it.
- Picker modes do not change: auto-launch is already off when `flag != FLAG_LAUNCH_APP`.

**Firing**
- Only on submit or a tip tap, as with Dial.
- Tip preview and toast follow the **system clock and locale**, not a fixed 24 h format. The parser refuses to
  guess am/pm, so the preview is the user's only chance to catch 07:30 vs 19:30:
  - time: `android.text.format.DateFormat.is24HourFormat(context)` picks the skeleton `Hm` or `hma`, which goes
    through `DateFormat.getBestDateTimePattern(locale, …)`. The result is `7:30 AM` or `07:30`.
  - date: `getBestDateTimePattern(locale, "EEEdMMM")`, so `Fri, Oct 3` in en-US, `Fri 3 Oct` in en-GB, and
    the platform's pattern in et (not hand-written).
  - timer: hours, minutes and seconds (`10 min`, `1 h 30 min`), never `10:00`, which reads as either 10 min or
    10 h.
  - all-day event: the date followed by `all day`.
  - Formatting lives on the Android side (`SystemActions`/fragment). The parser stays Android-free.
- Example previews (en-US, 12 h): `↵  Alarm 7:30 AM`, `↵  Timer 10 min`, `↵  Event Fri, Oct 3, 3:00 PM · dentist`.
- Alarm and timer send `EXTRA_SKIP_UI=true` and show a toast.
- An event opens the calendar editor, and the user confirms there.

**Must not parse** (each returns `None`)
- Bare keywords and plurals: `alarm`, `alarms`, `timer`, `timers`, `event`, `remind`, `reminders`, `calendar`.
- App-like names: `alarmy`, `alarm clock`, `timer+`, `timer 2`, `eventbrite`, `events 2026`, `äratuskell`.
- Out-of-range values: `alarm 25:00`, `alarm 7:61`, `timer 0m`, `timer 25h`.
- No title: `event tomorrow`.
- A query with a leading space.
- **Deliberately not parsed in 6.0.** These are common phrasings, but each one widens the grammar. They fall
  through to app search or the web tip, and nothing fires:
  - relative times: `remind me in 20 min`, `alarm in 8 hours`;
  - filler words: `timer for 10 minutes`, `alarm for 7:30`, `set alarm 7:30`, `set a timer 5m`;
  - verb-first phrasing: `wake me at 7`, `remind me tomorrow` (no time, no title).

**Focus and mindful pause**
- Alarm and timer bypass Focus. No app UI opens: with `SKIP_UI` the Clock only acknowledges.
- **Event also bypasses Focus, on purpose.** The Calendar editor opens even when the calendar app is not on the
  Focus whitelist. The editor only writes: the user types a title and saves, and nothing in it feeds attention.
  Blocking it would turn "note the dentist" into "break focus first". Unverified: some calendar apps land on their
  main view after Save instead of returning to Parem. That would leave the user in a non-whitelisted app during
  Focus, so it is a device check below. If Samsung Calendar does this, the fix is one line in the event branch
  (`FocusModeManager.isAppAllowed` on the resolved handler, then the blocked toast), not a design change.
- **The mindful pause never applies.** Quick actions call `startActivity` directly and never go through
  `BadHabitDialogs`' launch gate. So there is no pause, and nothing can fire either before or after one. That
  includes a Clock or Calendar app with a time limit. The gate stays a per-launch-of-an-app concept: a quick
  action is not a launch.
- The PR description states both points for reviewers of the "Calm phone" theme.

## Exact scope

- **New `helper/QuickActionParser.kt`** (Android-free, `java.time`, minSdk 29):
  - `sealed interface QuickAction` with `Alarm(hour, minute, label?)`, `Timer(seconds, label?)` and
    `Event(start: LocalDateTime, allDay, title)`.
  - `parse(query, now: LocalDateTime): QuickAction?`
  - `isActionPrefix(query): Boolean`, which is the auto-launch guard.
- **New `QuickActionParserTest.kt`**:
  - must-parse and must-not-parse tables in en and et, including the deliberate not-parse phrasings;
  - the `isActionPrefix` table;
  - `now` edge cases: 23:59, "sunday" on a Sunday, a time already past.
- **`helper/OmniboxResolver.kt`**:
  - `OmniboxMode.QuickAction(action)`;
  - a param `now: LocalDateTime = LocalDateTime.now()`;
  - one block after WebSearch.
- **`SearchMatcherTest.kt`**: one case pinning "Alarmy" vs `alarm ` / `alarm 7` (see Test plan).
- **`OmniboxResolverTest.kt`**: precedence cases.
  - `" alarm 7:30"` gives WebSearch.
  - A contact named "Timer" plus `timer 10m` gives QuickAction.
- **`helper/SystemActions.kt`**: `fireQuickAction(context, action): Boolean`.
  - Builds the intent and converts times with `ZoneId.systemDefault()`.
  - Catches `ActivityNotFoundException` and returns false.
  - Also holds the locale-aware preview formatting (`is24HourFormat`, `getBestDateTimePattern`).
- **`ui/AppDrawerFragment.kt`**:
  - new branches in the tip text, submit and tip-click `when`s;
  - `autoLaunchGuard` also checks `!QuickActionParser.isActionPrefix(...)`.
- **`AndroidManifest.xml`**: comment only. `<!--Used only for opening alarm app-->` becomes
  `<!--Opens the clock app; sets alarms and timers typed in the omnibox (normal-level, no runtime prompt)-->`.
  Data safety, the privacy policy and M4-WP19's F-Droid metadata describe permissions from this comment.
- **Strings** (`translatable="false"`, like the other hints): `alarm_hint`, `timer_hint`, `event_hint`,
  `quick_action_sent`, `quick_action_no_app`, `onboarding_omnibox_actions`
  (`alarm 7:30, timer 10m, event friday 3pm dentist`). The last one is added to the omnibox page's list in
  `OnboardingPagerAdapter`. See "Discoverability" for how this coordinates with M4-WP12.
- **`CHANGELOG.md`**: one `[Unreleased]` line.
- No prefs, no settings row, no new permission.

## Discoverability

- **In-app:** one line on the onboarding omnibox page, next to calc, dial and web: `onboarding_omnibox_actions`.
  This costs one string and one list entry.
- **Conflict with M4-WP12.** DECISIONS.md (M4-WP12) drops the feature tour, and `OnboardingPagerAdapter` with it,
  so this line lives only until M4-WP12 lands. That problem is bigger than WP15: calc, dial, web, bangs and
  M4-WP14 shortcuts all lose their only in-app mention at the same time. I'm adding the line anyway, because WP15
  may merge first and the line costs nothing. M4-WP12 needs Patric to choose one of these:
  - (a) keep one "What you can type" screen reachable after setup;
  - (b) a rotating `queryHint` on the empty drawer, replacing `___` (for example `2+2 · alarm 7:30 · !w calm`);
  - (c) rely on the store listing and screenshots.
  I'd pick (b): it is zero screens, it appears exactly where the feature lives, and it is one string array.
  It is not this WP's call.
- **Store:** M4-WP10's screengrab test types `alarm 7:30` into the drawer and captures the tip. That needs no
  onboarding at all. One line goes in the en/de/et listing text.

## Done criteria

- Every parser and resolver table is green, and the existing tests still pass.
- On an emulator, each action reaches Clock/Calendar with the right values.
- If no app handles the intent, the user gets a toast and nothing crashes.
- The mode is never set while the drawer is in picker mode (`flag != FLAG_LAUNCH_APP`).
- With Alarmy or "Multi Timer" installed and auto-launch on, typing `alarm 7:30` or `timer 10m` never opens the app.
- Previews follow the system 12/24 h setting and locale.
- The manifest comment matches what the permission is used for.

## Risks & traps

- **Misfire.** In action mode, submit fires the action instead of `launchFirstInList()`. The grammar and
  must-not table guard this.
- **`EXTRA_SKIP_UI` is advisory.** Some clock apps show their UI anyway, so the toast says "sent to Clock" and
  not "set".
- **Auto-launch race.** The adapter auto-launches the single match before the action can resolve. Mitigated by
  `isActionPrefix` (above). The JVM table plus the device check cover it.
- **Focus/mindful pause are bypassed**, like Dial — deliberate, including the Calendar editor; see "Focus and
  mindful pause". Say so in the PR.
- **Onboarding line is short-lived** if M4-WP12 deletes the tour; see "Discoverability".
- **Inject `now`**, or tests flake at midnight.

## Test plan

- **JVM:** parser and resolver tables (most of the work).
- **JVM, auto-launch:** `isActionPrefix` table in `QuickActionParserTest`:
  - true: `ala`, `alarm`, `alarm `, `alarm 7`, `timer `, `timer p`, `remind m`, `äratus 7`, `eve`;
  - false: `al`, `alarmy`, `ever`, `timers`, ` alarm 7:30`, `calendar`.
  Also add one `SearchMatcherTest` case pinning the facts the rule relies on: "Alarmy" matches `alarm ` but not
  `alarm 7`. If the matcher changes, the guard gets revisited.
- **Emulator** (Google Clock and Calendar): fire each action, then disable Calendar to check the toast path.
- **Device (Patric):**
  - check that Samsung Clock and Calendar honour the extras and `SKIP_UI`;
  - install Alarmy and a "Multi Timer", turn auto-launch on, and type `alarm 7:30` and `timer 10m` at normal
    speed. Neither app opens, the tip shows, and Enter sets it. Then type `alarmy`: it auto-launches as before;
  - set the phone to 12 h and then to 24 h, and check the preview each time;
  - with Focus on and Calendar not whitelisted: `event friday 3pm dentist`, save, and note whether you land back
    in Parem or in the calendar's main view.

## Not verified

- **Play policy.** The Play policy page itself was not read. SET_ALARM is normal-level and is not
  `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM`, which are the ones Play restricts, so no declaration is expected.
- **OEM handling.** How OEM clock apps treat `EXTRA_SKIP_UI` and `EXTRA_MESSAGE`, and how calendar apps treat
  `TITLE`.
- **Estonian phrasing.** Two choices need Patric:
  - `kohtumine` vs `sündmus`;
  - whether `tuleta meelde` is what people actually type.
- **Calendar return after Save** (see Focus): not checked on any OEM calendar.

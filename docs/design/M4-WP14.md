# M4-WP14: Omnibox app shortcuts (design proposal)

Status: proposal, revised after review (see "Review notes"), awaiting sign-off. Base: `origin/next`.

## Problem

Typing "liked" or "incog" finds nothing today. Apps publish shortcuts (Spotify "Liked Songs", Chrome "New Incognito
tab", Maps "Home") that Pixel users expect search to reach. Platform facts (AOSP
[LauncherApps.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/content/pm/LauncherApps.java),
[reference](https://developer.android.com/reference/android/content/pm/LauncherApps)):

- `getShortcuts(query, user)`, `startShortcut(...)` and `getShortcutIconDrawable(...)` need `hasShortcutHostPermission()`,
  which only the current default launcher has. Without it the service throws `SecurityException("Caller can't access
  shortcut information")` ([LauncherAppsService](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/pm/LauncherAppsService.java)).
- All three throw `IllegalStateException` when the target user is locked or not running (Private Space locked, work
  profile paused). `startShortcut` throws `ActivityNotFoundException` for a removed/disabled shortcut.
- `ShortcutQuery.setPackage(null)` returns every package's shortcuts: one IPC per profile.
- `FLAG_MATCH_PINNED` only returns shortcuts pinned *by Parem*. M4-WP7 chose not to accept pin requests, so it is always
  empty today. `FLAG_MATCH_CACHED` holds notification conversation shortcuts.
- `Callback.onShortcutsChanged` fires on shortcut changes without a package change. `PackageChangeTracker` doesn't
  override it.

No new permission or manifest change: no Play/Data-safety impact.

## The auto-launch constraint (decides the query shape)

`AppDrawerAdapter.autoLaunch` fires when exactly one row is listed (`itemCount == 1`), with no pref. Only a leading
space, a leading `!` or CJK composing vetoes it. So in "spotify liked" or "maps home" the app prefix ("spo", "map")
usually narrows to one app and launches it before the second word is typed. Two ways out:

| | Rule | Cost |
|---|---|---|
| **1. Shortcut-label queries** (chosen) | Auto-launch is unchanged. Shortcuts are reached by their own label ("liked", "incog"). "app + label" is a bonus that works only when the app word doesn't narrow to one app row | The roadmap's "maps home" / "spotify liked" examples don't work for a typical install |
| 2. Wait when the single app has shortcuts | Auto-launch holds when the single matching app publishes shortcuts | Breaks auto-launch for most big apps (Maps, Chrome, Spotify, WhatsApp, Gmail all publish shortcuts). "maps" would no longer open Maps. That regresses the drawer's core gesture for a secondary feature |

**Rule 1.** Precisely:
- Auto-launch counts **app rows only** (`shortcutId == null`): `filteredSnapshot.count { it.shortcutId == null } == 1`
  replaces `itemCount == 1`. With no shortcut rows this is identical to today (header/padding rows count as before).
  So every query that auto-launched before still auto-launches, and a shortcut row never stops or triggers it.
- `firstApp()` skips shortcut rows when it picks the auto-launch target. App rows always come first anyway.
- Consequence, stated: a shortcut is reachable only when the query matches **zero or ≥2 app rows**. "liked" and "incog"
  match no app, so they work. "hom" with Google Home installed auto-launches Google Home before "home" is complete,
  exactly as today. "maps home" works only when "maps" matches ≥2 app rows (personal + work Maps), or with the
  existing leading-space escape (" maps home": no auto-launch, rows are listed and tappable, Enter is a web search).

## Options

| | What | Cost | Tradeoffs |
|---|---|---|---|
| A. Rows in the drawer list | Matching shortcuts become extra rows after all app rows | ~170 LOC, 1 pure helper | Reuses limits, pause, focus, profile badge and icons |
| B. Tip line only (like Contact) | The best match fills `appDrawerTip` and submit launches it | ~80 LOC, an `OmniboxMode` | Only one result, and it fights calc/contact for the tip. "Liked Songs" vs "Search" can't be chosen |

## Recommendation

**A**, with dynamic + manifest + pinned, no cached. Shortcut rows show the parent app's icon, with no shortcut
icon in 6.0. A per-shortcut icon means a binder/file read per bind.

Matching rule (pure, JVM-tested):
- The normalized query must be at least 3 characters.
- **Single-token query:** `SearchMatcher.matches(shortLabel, shortKey, query)`, on the shortcut label alone. A substring
  or initials match never crosses into the app label ("sho" doesn't hit "Maps Home").
- **Multi-token query (≥2 tokens):** also `SearchMatcher.matches("$appLabel $shortLabel", combinedKey, query)`. This
  is the "maps home" path, live only under the rule above.
- In both cases the shortcut is dropped when the query matches its **app label alone**. "maps" stays an app search and
  never adds Maps' own shortcuts.
- Order: app label, then `rank`; cap 5.

## Exact scope

- **New `helper/ShortcutMatcher.kt`** (Android-free):
  - `data class Raw(packageName, userKey, id, shortLabel, rank)` is what the system returns and what gets cached.
  - `data class Entry(raw, appLabel, shortKey, combinedKey)`. `entries(raw: List<Raw>, appLabels: Map<String, String>
    /* "pkg|user" → displayed label */)` builds the keys and drops any `Raw` whose "pkg|user" isn't in the map.
  - `filter(entries, query, limit = 5): List<Entry>`.
- **`helper/PackageChangeTracker.kt`**: add a separate `shortcutStamp` that `onShortcutsChanged` bumps. Not
  `invalidate()`, which would wipe icon caches on every chat app's shortcut update.
- **`helper/AppListSource.kt`**: add `getShortcutRaws(context): List<ShortcutMatcher.Raw>` on IO. It:
  - returns empty unless `hasShortcutHostPermission()` (catch `IllegalStateException`);
  - skips **every** profile where `userManager.isQuietModeEnabled(profile)` (paused work profile, locked Private Space)
    before querying. That skip counts as complete. Unpausing/unlocking already bumps `stamp()` via
    `onPackagesAvailable`, so the cache refills then;
  - runs one `getShortcuts` per remaining profile with `FLAG_MATCH_DYNAMIC|MANIFEST|PINNED`, keeps only `isEnabled`;
  - catches `IllegalStateException`/`SecurityException` per profile (profile stopped but not quiet) → partial;
  - snapshot-caches **only `Raw`** like `RawAppSnapshot`, keyed on (`stamp()`, `shortcutStamp()`), and never caches a
    partial or no-permission result. No labels are cached, so a rename (which bumps neither stamp) can't go stale.
    The same rule as `getAppsList`, which re-applies renames per call.
- **`data/AppModel.kt`**: add `shortcutId: String? = null` and `shortcutLabel: String? = null`. A shortcut row is
  `parentApp.copy(key = null, activityClassName = null, isNew = false, shortcutId = id, shortcutLabel = shortLabel)`,
  where `parentApp` is the visible app row for "pkg|user". So:
  - `appLabel` = the parent app's displayed (renamed) label. `BadHabitDialogs.gateLaunch` and the focus/limit paths
    name **the app** ("Spotify"), never "Liked Songs";
  - `appPackage`, `user`, `isPrivate` = the parent's. Limits, mindful pause, `FocusModeManager.isAppAllowed`, the
    profile badge and the `AppOpenCounter` private guard apply unchanged;
  - `activityClassName = null`, `url = null`. Neither is read, because `selectedApp` returns before `launchApp`.
  - If a package has two launcher activities (two rows for one "pkg|user"), the first row is the parent.
- **`helper/DrawerRows.kt`**: `decorate` gains `isShortcut: (T) -> Boolean`. Order: regular app rows, header, private
  app rows, **shortcut rows** (in matcher order, private parents included), padding. Both splits are stable
  partitions. This keeps shortcuts under every app row, including private app rows with Private Space unlocked.
  Appending in `performFiltering` alone would put them above private rows.
- **`ui/AppDrawerAdapter.kt`**:
  - `@Volatile var shortcutRaws` plus a derived `@Volatile shortcutEntries`, rebuilt by `ShortcutMatcher.entries` in
    `setAppList` and when raws are set. The label map comes from the gated `appsList`. Hidden apps, locked private
    apps and other users are excluded by construction. Renames show up on the next `setAppList`;
  - `performFiltering` appends matched rows (only when `flag == FLAG_LAUNCH_APP` and the query is non-blank), and
    `decorate()` places them;
  - auto-launch / `firstApp()` as in the rule above;
  - `DIFF_CALLBACK` identity adds `shortcutId`. The row shares its package with the app row;
  - bind: `shortcutLabel` in `appTitle`, `appLabel` in `appUsageTime`, and no long-press menu. Hide/rename/uninstall on
    a shortcut row would act on the parent app.
- **`ui/AppDrawerFragment.kt`**: when `flag == FLAG_LAUNCH_APP`, load raws in `lifecycleScope` (guard
  `isAdded`/`_binding`) and set them on the adapter. Re-filter only if the query is non-blank **and** the published
  list doesn't have exactly one app row. Shortcuts can't change the app-row count, so a one-app result has already
  auto-launched, and re-filtering would fire it twice.
- **`MainViewModel.selectedApp`**, in the `FLAG_LAUNCH_APP`/`FLAG_HIDDEN_APPS` branch: the url branch first, then the
  `FocusModeManager` check, **then** `if (appModel.shortcutId != null) { launchShortcut(appModel); return }`, before
  and never falling through to `launchApp`. `launchShortcut` calls `launcherApps.startShortcut(pkg, id, null, null,
  user)` and bumps `AppOpenCounter` only if `!isPrivate`. Any exception shows the toast `unable_to_open_app`
  (existing string), including `SecurityException` when Parem stopped being the default home after the list loaded
  (the rows are then stale until the next drawer open). The bad-habit pause runs in the fragment
  (`checkBadHabitAndLaunch`) before `selectedApp`, so it applies to shortcut rows as-is.
- **Submit (Enter), intended change:** `onQueryTextSubmit` stays as is. `itemCount == 0` → `openSearch`, else
  `launchFirstInList()`. A query that matches **only shortcut rows** ("liked") therefore launches the first shortcut
  on Enter, through the pause/focus gates, instead of opening a web search. And the `no_apps_found` tip doesn't show,
  because there are results. That's deliberate: Enter launches the top listed result, as it does for apps. When app
  rows exist they come first, so Enter on a mixed list launches the app as before.
- **Not touched, a departure from the roadmap row:** row M4-WP14 lists `helper/OmniboxResolver.kt`. Shortcuts are
  drawer rows, not an `OmniboxMode` (option B was rejected), so the resolver has nothing to resolve. Prefs, strings
  and the manifest are also untouched.
- **`CHANGELOG.md`**: one line.

## Done criteria

- With Parem as default home, "liked" / "incog" lists the shortcut and launches it on tap or Enter. Any app rows
  stay above the shortcut rows, private app rows included.
- Every query that auto-launched before still does ("maps", "chr"), and a shortcut row never auto-launches.
- Not default: no rows, no error. Stopped being default mid-session: tap → `unable_to_open_app`, no crash.
- Locked Private Space or paused work profile: zero shortcut rows from that profile, and the result is cached (no IPC
  per drawer open). Hidden app: zero rows.
- A limited or bad-habit app's shortcut shows the pause, naming the app. Focus blocks a non-whitelisted app's shortcut.
- Renaming an app: its shortcuts match the new name on the next drawer open.
- JVM suite and `assembleDebug` green.

## Risks & traps

- **Trap #5:** the shortcut cache must check both stamps, or a fresh install/update serves dead IDs.
- Auto-launch must count app rows only. Counting shortcut rows would let any shortcut label (including chat names in
  dynamic shortcuts) silently stop an app's auto-launch.
- The rows need their own DiffUtil identity (same package as the app row).
- Dynamic shortcuts can hold contact names. They appear only on a typed query, and `CACHED` is excluded.
- Private shortcuts must never reach `AppOpenCounter` (exported).

## Test plan

- **JVM** `ShortcutMatcherTest`:
  - "liked" → Liked Songs; "maps" doesn't list Maps' shortcuts (it matches the app label);
  - "maps home" matches through the multi-token path;
  - "sho" does **not** match Maps/"Home" (no cross-boundary hit on a single token);
  - diacritics ("cafe" vs "Café"); under 3 chars none;
  - a Raw whose "pkg|user" isn't in the label map is dropped (hidden, private-locked, other user);
  - a renamed label: `entries(...)` with a new map matches the new name and not the old one;
  - cap 5 and order.
- **JVM** `DrawerRowsTest`: regular + private + shortcut rows (with a header) → regular, header, private, shortcuts,
  padding. A private app row stays above a regular app's shortcut row. Usage order is kept within each section.
- **Emulator** (API 35, Google APIs image, Chrome manifest shortcuts):
  - set as default → "incog" lists "New Incognito tab". Tap launches it. Enter launches it (no web search);
  - "chr" still auto-launches Chrome;
  - switch default to Launcher3 → nothing shown and no crash;
  - Private Space unlocked, with a query that matches a private app and a regular shortcut → private app row above the
    shortcut row. Lock → private shortcuts gone;
  - disable Chrome via adb → row gone (stamp).
- **Device:** Maps/Spotify dynamic shortcuts, paused work profile (no rows, no repeated IPC: one log line per stamp),
  mindful pause naming the app, OEM skin.

## Not verified

- `getShortcuts` behaviour on OEM skins (MIUI/One UI), and how often real apps fire `onShortcutsChanged`.
- Chrome manifest shortcuts on the emulator image. Nothing was built or run.
- That `onPackagesAvailable` fires for Private Space unlock as it does for work-profile unpause (else the quiet-skip
  cache would hold until another package change). Verify on the emulator; fallback: also key the cache on the set of
  quiet profiles.
- Open question: a Settings toggle? Recommended no: query-only, and off when not default.

## Review notes

- **Auto-launch blocker:** accepted. Rule 1 was chosen over rule 2 (see the table). Examples and the emulator step
  moved to "liked"/"incog". "chrome incog" would have auto-launched Chrome at "chr".
- **Ordering:** accepted. A shortcut section in `DrawerRows.decorate` with a JVM test, rather than appending after
  `decorate()` in the adapter, so the order lives in the one tested place.
- **Rename staleness:** accepted. Only `Raw` is cached, and labels are joined per app list.
- **Paused profile:** accepted. A quiet-mode skip for every profile, counted as complete.
- **Submit:** decided as intended (Enter launches the top result) and tested.
- **AppModel mapping, selectedApp position, default lost mid-session:** specified above.
- **Cross-boundary matching:** fixed by matching on the shortcut label alone for single tokens.
- **Roadmap drift:** stated under "Not touched". The row's done criterion ("listed under app results, never above")
  is kept, but its examples ("maps home", "spotify liked") are only reachable in the cases rule 1 names.
  Proposing the roadmap row's examples be updated to "liked"/"incog" at close.

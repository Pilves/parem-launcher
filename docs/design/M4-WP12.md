# M4-WP12 — Onboarding for 6.0 (design)

## Problem

A fresh install runs two flows at once: `MainActivity.onCreate` fires `resetLauncherLiveData` on `firstOpen` (the `ROLE_HOME` dialog on Q+), while `HomeFragment.onViewCreated` opens `OnboardingFragment`. The user gets a system dialog with no context over a 5-page tour that never asks for home again; afterwards only the small `setDefaultLauncher` text on home remains. The tour's "Double tap to lock" line will need M2-WP5's consent. No Calm-phone feature is reachable from onboarding.

Code facts: onboarding is `ui/OnboardingFragment.kt` + `ui/OnboardingPagerAdapter.kt` (no `ui/onboarding/` package; the roadmap "Owns" is wrong). Gate: `prefs.onboardingVersionSeen < Constants.ONBOARDING_VERSION` (2), written *before* navigating.

## Options

- **A. Add pages to the pager** (home first, Calm last). Smallest diff, but home is one swipe-past away and there are 7 pages.
- **B. Two screens replace the tour (recommended).** "Make Parem your home", then "Calm phone (optional)": 4 rows, each running its owning WP's turn-on flow. Cost: the tour is dropped; its translated strings stay unused (flagged, not deleted).
- **C. Home only; Calm setup stays in Settings.** Least code; misses the 6.0 story for new users and upgraders.

## Recommendation

B. Fewer screens, more finishers; the 90% target measures screen 1 only. Dropping the tour is Patric's call (Not verified).

## Exact scope

- **`ui/OnboardingFragment.kt`**: rewrite it as two states in one fragment (a `ViewFlipper` or two child layouts; no pager, no dots). Delete `OnboardingPagerAdapter.kt` and `item_onboarding_page.xml`.
  - **Screen 1 (Home):** a title, one line ("Parem only works as your home screen"), the primary "Set as home" and a dimmed "Not now".
    - Primary calls the existing `viewModel.resetLauncherLiveData.call()` (role dialog on Q+, FakeHomeActivity chooser before Q). After one cancelled role result it opens `ACTION_HOME_SETTINGS` instead, falling back to `ACTION_MANAGE_DEFAULT_APPS_SETTINGS` in `try/catch`.
    - `onResume`: if `isDefaultLauncher()`, advance to screen 2. This one check covers every route. Upgraders already on Parem start on screen 2.
  - **Screen 2 (Calm):** four rows showing "Set up"/"On", re-derived in `onResume`, each calling its owner's entry function:
    | Row | Calls | Shown when |
    |---|---|---|
    | Filtered notifications | M4-WP1 turn-on flow (allowlist → disclosure → listener settings) | API ≥ 26 |
    | Mindful pause | M4-WP2 habit-app picker | always |
    | Grayscale | M4-WP5 grant sheet (wireless pairing primary, per DECISIONS) | always |
    | Double tap to lock | M2-WP5 `showLockConsent`; accept routes to accessibility settings, decline does nothing (double-tap keeps the M2-WP5 first-use consent) | API ≥ 28 |

    Contract: each owner exposes `fun start…Setup(fragment: Fragment)`; an unmerged WP's row is absent. One "Done" pops back; not tapping a row is the skip.
- **`MainActivity.kt`** (outside listed ownership, required): remove `resetLauncherLiveData.call()` from the `firstOpen` block; device-check the `RESULT_OK` branch (Risks).
- **`Constants.ONBOARDING_VERSION` 2 → 3**, so every 6.0 upgrader sees screen 2 once.
- `HomeFragment` keeps writing the gate before navigating (no re-entry loop on recreate). Rework `fragment_onboarding.xml`; ~12 strings `translatable="false"`; one CHANGELOG line. No new prefs (role-cancel memory is a fragment field). Callbacks guard on `isAdded`.

## Done criteria

- A fresh install shows screen 1, and no role dialog appears before the user taps.
- Granting home on Q+, pre-Q, and through the settings fallback all land on screen 2 without further taps.
- "Not now" and back both reach screen 2 and then home. The `setDefaultLauncher` home link still works.
- Each Calm row runs its owner's flow. Returning from it shows the correct state. Declining any flow leaves that feature off.
- Upgrade from v5.x with Parem as default: screen 2 only, shown once.
- `compileDebugKotlin`, `testDebugUnitTest` and `assembleDebug` exit 0.
- Closed test: ≥ 90% of testers report Parem is their home after onboarding.

## Risks & traps

- **Measuring 90%.** No analytics, ever. Use the closed-test feedback form ("Is Parem your home screen now?") plus 3–5 watched first-runs.
- **Possible bounce to Settings after success.** On `RESULT_OK`, `MainActivity` calls `resetLauncherViaFakeActivity()`, which opens Default-apps settings whenever the default package contains "." — Parem included. If confirmed, skip that call on `RESULT_OK`.
- **Role re-request.** The docs only promise `RESULT_OK`/`RESULT_CANCELED` ([RoleManager](https://developer.android.com/reference/android/app/role/RoleManager#createRequestRoleIntent(java.lang.String))). The dialog may be suppressed after a denial; the settings fallback ([ACTION_HOME_SETTINGS](https://developer.android.com/reference/android/provider/Settings#ACTION_HOME_SETTINGS), [ACTION_MANAGE_DEFAULT_APPS_SETTINGS](https://developer.android.com/reference/android/provider/Settings#ACTION_MANAGE_DEFAULT_APPS_SETTINGS) — "a matching Activity may not exist") covers that case.
- Becoming home may restart the activity: `onResume`, not a result callback, is the source of truth.
- Sideloaded 13+: M4-WP1/M2-WP5 restricted-settings lines apply unchanged. Grayscale (pairing) is slow; label it "one-time setup, ~2 min". Traps #1–#5 untouched.

## Test plan

No pure logic, no JVM tests. Devices: API 34+, 29, and a 24–28 emulator. Fresh install grant / deny / deny-then-settings; back and "Not now"; rotate; kill inside the role dialog; upgrade over v5.7.0 as default and not; each Calm row accept / decline / return ungranted; sideloaded API 33+.

## Not verified

- Whether `ROLE_HOME` re-prompts after a denial, and whether OEM ROMs return `RESULT_OK` reliably. Needs a device.
- The settings bounce after `RESULT_OK`, described above.
- Patric's sign-off on dropping the feature tour, versus keeping it as an optional "Tips" link on screen 2.
- The entry-function names: M4-WP1/2/5 and M2-WP5 have not merged yet, and each must expose its `start…Setup`.

# M4-WP13 — Adaptive layouts for API 37 (design)

## Problem

When an app targets API 36, displays with sw ≥ 600dp ignore its `screenOrientation`, `resizeableActivity`, min/max aspect ratio and `setRequestedOrientation()` [1][2]. Games are exempt, and so is a user who chooses "app default" in aspect-ratio settings. API 36 has an opt-out, `PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY`, and API 37 removes it. Parem already targets 36 and doesn't use the opt-out, so these rules **already apply** on Android 16 tablets and foldables. Below sw600 the orientation lock is still honoured.

Inventory (origin/next):

- `MainActivity.setupOrientation()` locks portrait unless `isTablet()` (diagonal ≥ 7" from `displayMetrics`) or API 26 (the `windowIsTranslucent` + fixed-orientation crash). The docs advise against device-type checks like this [3], and it doesn't match the platform's sw600 rule.
- **Stale lock:** when `isTablet()` is true, the function returns without resetting the orientation. On a foldable with API ≤ 35, a fold followed by an unfold can therefore keep the portrait lock (not verified).
- `WallpaperUtils.setWallpaper()` is the other `isTablet()` caller.
- Manifest: `configChanges="uiMode"` only, so a size change recreates the activity and resources are re-selected. No opt-out property.
- `layout/` has 11 files. `layout-land/` has 3:
  - `fragment_home` (the tablet **widget column**)
  - `fragment_app_drawer` (56dp `marginHorizontal` on the header row and the RecyclerView; tip `marginStart` 76dp)
  - `fragment_settings` (literal `paddingHorizontal="100dp"` on the ScrollView)

  There are no `sw`/`w` qualifiers. In tablet portrait (Pixel Tablet ≈ 800dp wide), on unfolded large phones and in 600–839dp split-screen halves, the phone layout stretches edge to edge (settings, drawer, onboarding).
- `BottomSheetMenu` and `FocusModeDialog` are `BottomSheetDialog`s, forced to `STATE_EXPANDED` with `skipCollapsed`. Material caps their width at 640dp by default [4]; nothing caps their height.

## Options

| | Approach | Cost | Tradeoff |
|---|---|---|---|
| A | Opt-out property | 1 line | Gone at API 37, and desktop windowing overrides it anyway [2]. |
| B | `androidx.window` `WindowSizeClass` [5] | New dependency, code in each fragment, recompute plumbing | Nothing in Parem needs a runtime decision that resources can't express. |
| C | **Resource qualifiers** [3] | A few XML values, ~5 lines of Kotlin | Automatic on recreate. Width cap comes in steps. |
| D | Drop the portrait lock everywhere | Small | Phones would get the tablet `layout-land`. Phone home-screen rotation was deliberately removed. |

## Recommendation

**C.** No dependency and no Compose. Keep the portrait lock below sw600, release it at sw600 to match the platform, and cap the reading width of settings and the drawer at every width from 600dp up.

## Exact scope

1. Add `<bool name="lock_portrait">` to `res/values/bools.xml` (`true`) and to `res/values-sw600dp/bools.xml` (`false`).
2. `MainActivity.setupOrientation()`:
   - if `getBoolean(R.bool.lock_portrait)`, set `SCREEN_ORIENTATION_PORTRAIT`
   - **otherwise set `SCREEN_ORIENTATION_UNSPECIFIED`**, which fixes the stale lock

   No `SDK_INT` check (see Sequencing).
3. In `WallpaperUtils.setWallpaper()`, replace `isTablet(appContext).not()` with `getBoolean(R.bool.lock_portrait)`. Then delete `isTablet()` from `helper/Utils.kt`; it has no other callers.
4. Add `dimen content_side_padding`. Resource selection ranks `w<N>dp` above `land`, so the width steps win whenever they match:

   | File | Value | Content width in the band |
   |---|---|---|
   | `values/` | 0dp | phone portrait, full width |
   | `values-land/` | 100dp | landscape windows narrower than 600dp (today's settings value) |
   | `values-w600dp/` | 64dp | 472–711dp (tablet portrait, unfolded, split halves) |
   | `values-w840dp/` | 200dp | 440–799dp |
   | `values-w1200dp/` | 360dp | 480–879dp |
   | `values-w1600dp/` | 520dp | 560–880dp (up to 1920dp) |

   The padding applies once per side. Inner padding that already exists (the settings `scrollLayout` and the drawer rows) adds to it.
5. Apply it:
   - **Settings:** use it as `paddingHorizontal` on the `scrollView` ScrollView in both `fragment_settings` variants, replacing the 100dp literal in `layout-land`. Both already have `clipToPadding="false"`, so nothing else changes there.
   - **Drawer:** use it as `paddingHorizontal` on the **root `FrameLayout`** of both `fragment_app_drawer` variants. That way the header row, `appDrawerTip` and `recyclerView` all move in together. In `layout-land`, delete the 56dp `marginHorizontal` from the header row and the RecyclerView, and change the tip's `marginStart` from 76dp to 20dp to match portrait. Otherwise the insets stack (256dp per side at w840). Below w600, landscape goes from 56dp to 100dp per side; that only happens in narrow landscape windows. Cost: rows narrow, and touches in the side bands no longer scroll the list. That's acceptable for a reading list.
   - No `clipToPadding` changes are needed. The settings ScrollViews and the drawer RecyclerView already set it to false, and padding on the root FrameLayout doesn't clip scrolling content.
6. Home: no change, because `layout-land` and its widget column already serve wide windows. Sheets: no code change, but they are checked (see Done criteria).
7. Prefs and strings: none. Manifest: none, and the opt-out is not added.
8. `SmokeTest.rotatesOnLargeScreenOnly()`: call `device.setOrientationLandscape()`.
   - If `smallestScreenWidthDp ≥ 600`, assert that home is shown and that `openDrawer()` passes.
   - Otherwise, assert `displayRotation == 0`.

   Restore with `setOrientationNatural()`.
9. `smoke.yml`: list the four legs explicitly under `include`. Today `api-level` is hardcoded to 34 and isn't an axis. That means an `include` entry such as `{profile: pixel_tablet, api-level: 36}` would just add a key to the existing tablet job instead of creating a fourth job.
   ```yaml
   strategy:
     fail-fast: false
     matrix:
       include:
         - { profile: pixel_6,      api-level: 34, perf: true }
         - { profile: pixel_fold,   api-level: 34 }
         - { profile: pixel_tablet, api-level: 34 }
         - { profile: pixel_tablet, api-level: 36 }
   ```
   - Pass `api-level: ${{ matrix.api-level }}` and `profile: ${{ matrix.profile }}` to emulator-runner [6].
   - The perf run stays on `pixel_6` only, so the baseline stays comparable. emulator-runner runs each `script` line separately, so put the condition on one line: `if [ "${{ matrix.perf }}" = "true" ]; then ./gradlew installDebug && node scripts/perf-budget.mjs --out app/build/perf/result.json; fi`.
   - Suffix the artifact names with `-${{ matrix.profile }}-${{ matrix.api-level }}`, because upload-artifact v4 rejects duplicate names across jobs. Upload the perf artifact only from the perf leg.
   - **Fallback**, if a leg is missing its image or profile on the runner, or runs past `timeout-minutes: 45`: set `continue-on-error: ${{ matrix.profile != 'pixel_6' }}` on the job. The phone leg stays the only blocking check. Record the failure in the handoff, and move the large-screen legs to a `workflow_dispatch`-only job run on the RC commit. smoke.yml already runs only on PRs to master and on dispatch, so it never runs per commit on `next`. A flaky large-screen leg must not hold the 6.0 cut-off. The large-screen evidence then comes from the manual screenshots.
10. A CHANGELOG `[Unreleased]` line.

## Done criteria

- **Smoke matrix:** green on the phone, foldable, tablet (API 34) and tablet (API 36) legs, including the new test. If the fallback in step 9 was used, the handoff names each non-blocking leg and its last result.
- **Width cap:** at every window width W from 600dp to 1920dp, settings and drawer content has ≥ 64dp side inset on each side and is ≤ 880dp wide. Check it with screenshots at **600, 800 (tablet portrait), 839, 840, 1280 and 1920dp**. Nothing is clipped and no screen needs horizontal scrolling. Below 600dp, the phone layout is unchanged.
- **Sheets:** screenshots at 840, 1280 and 1920dp in landscape of three sheets:
  - the app long-press menu (`BottomSheetMenu`)
  - Focus (`FocusModeDialog`)
  - screen time (`ScreenTimeGraphDialog`)

  Each sheet must open fully expanded, have every row reachable by scrolling, and keep the last row clear of the navigation bar. Repeat on the tablet at a 50/50 top-bottom split, the short-window case. Material's 640dp cap only covers width.
- **Fold → unfold → fold** on the foldable emulator: home keeps working, and the lock applies only while folded.
- **Manual checks**, with screenshots attached to the PR. Each one's result is recorded in the handoff:
  - **Split screen 50/50**, on the phone and on the tablet in both orientations
  - **Desktop window** on the API 36 tablet (developer option "Enable desktop windowing")

  The pass condition is either of two outcomes:
  - Parem lays out correctly in the window.
  - The system won't window the HOME activity. In that case Parem is undamaged afterwards: back to fullscreen home with no stale lock or stretched layout.

  These checks stand in for the row's "desktop window" emulator-matrix entry. CI can't drive the emulator's desktop mode or split screen, so this is a deliberate substitution, not a silent narrowing (see Review notes).
- `compileDebugKotlin`, `testDebugUnitTest` and `assembleDebug` exit 0.

## Risks & traps

- **Recreate on resize:** this already happens on tablet rotation. It dismisses open sheets, which is acceptable, and re-runs `restoreWidgets()` (ARCHITECTURE trap #2). Don't add `screenSize|orientation` to `configChanges` to avoid it.
- **Lock view:** keep the invisible `lock` view in `layout-land/fragment_home` (trap #1).
- **Qualifier scope:** `values-sw600dp` and `w<N>dp` follow the window, while the platform's ignore rule follows the display. A fullscreen home window makes them equal. In a narrow split half on a tablet (sw < 600), `lock_portrait` is true, but the platform ignores the request on a large display anyway.
- **Table-top posture:** not handled. It needs `androidx.window` folding features, so it's 6.1 if testers ask. This is a cut against the row's Outcome (see Review notes).
- **Phone landscape:** stays unsupported. That is the product call made by rejecting D.

## Not verified

- That a `requestedOrientation` from `setRequestedOrientation` survives `recreate()` on API ≤ 35 (the stale-lock claim). Setting `UNSPECIFIED` explicitly is harmless either way.
- That the API 36 `google_apis` x86_64 image and the `pixel_fold`/`pixel_tablet` profiles exist on the runner, and what the matrix costs in CI minutes. Four legs instead of one, run in parallel, so wall-clock time should be similar and billed minutes about 4×. The step 9 fallback covers both.
- That `adb emu fold` works with `-no-window`.
- Whether the system ever puts the home task into split screen or a desktop window (see Review notes).

# M4-WP21 — Per-app grayscale (design proposal)

Status: proposal, revision 2. Base: `origin/next`. Builds on the controller specified in `M4-WP5.md`. No `feat/grayscale` branch exists on origin as of this revision, so every WP5 hook named below (`GrayscalePolicy.desired`/`plan`, `reconcile`, the `MainActivity.onStart`/`onStop` limit-override code) refers to the WP5 *design*, not merged code. **WP21 implementation starts only after WP5 is merged: rebase onto WP5's controller and re-check that the `desired()` signature, `plan()` actions and the `MainActivity` hooks still match this document before writing code.** Uses `ACTIVITY_RESUMED`, which has existed since API 29; with 6.0 at minSdk 29 (M4-WP20) no version gate is needed. Below 29 the same value (1) was `MOVE_TO_FOREGROUND`, so M4-WP20 is a convenience here, not a hard dependency. No accessibility service.

## Problem

Grey while a marked app is in front, colour elsewhere, including after switches that skip Parem. Never stuck grey.

## Options

| | Mechanism | Cost |
|---|---|---|
| **A** | `Handler` loop in Parem's own process, started in `MainActivity.onStop`, stopped in `onResume` | No service, no notification, no new permission. Relies on the home process not being frozen |
| B | Same loop in a `specialUse` foreground service | Two permissions, a subtype Play reviews ([types](https://developer.android.com/develop/background-work/services/fgs/service-types)), a notification per session. `onStop` start is not an exemption ([bg-start](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)) |
| C | WorkManager / JobScheduler | 15-minute floor. Useless for seconds |
| D | Exact alarms | Exact-alarm policy, a wakeup per tick |

## Recommendation

**A.** The home process sits at `HOME_APP_ADJ` = 600, not cached (≥ 900, [ProcessList](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/services/core/java/com/android/server/am/ProcessList.java)); Android 14 freezes only cached processes ([14 changes](https://developer.android.com/about/versions/14/behavior-changes-all)). So the feature requires Parem as default home. B only if the device pass shows the loop stalling.

### The gate

Per-app grayscale is active only when all three hold. One function, `GrayscaleController.appModeReady(ctx)`, checks them:

1. WP5's grant (`isGranted`)
2. usage access (`appUsagePermissionGranted`)
3. Parem is the default home (`isParemDefault`)

Every place that could write `APP_FG = true` checks the gate: the launch trigger and the watcher start. **With the gate closed, nothing sets `APP_FG` at all**, so a marked app simply stays in colour. That is why there is no stuck-grey case for "Parem opened from its app icon while another launcher is default": the launch trigger does not fire, and pressing Home, which goes to the other launcher, has nothing to undo.

The gate is also the setup flow (see "Marking an app"), so a marked app with an open gate means the user opted into everything the feature needs. If a condition is lost later (usage access revoked, a different default launcher), the feature quietly falls back to colour. That is the failure direction the row asks for.

### Session

**Session = Parem stopped while ≥1 app is marked and the gate is open**, so a notification tapped from home is covered too.

### Tick, 1000 ms

- `since` starts at the time of the last `MainActivity.onPause` (an in-memory field, `System.currentTimeMillis()`; if it is unset, e.g. after a process restart, use the `onStop` time). After each tick, set `since` to the timestamp of the last event read. If the tick read nothing, leave `since` as it is.
  - Why `onPause` and not `onStop`: the next app's `ACTIVITY_RESUMED` lands *between* Parem's pause and stop. Starting at `onStop` would miss the resume of an app opened from a notification on home, and that app would never turn grey.
- If `!PowerManager.isInteractive`, skip the query. No wakelock is held, so a dark screen costs nothing.
- If usage access is gone: set `APP_FG = false`, `reconcile`, and stop. Failure goes towards colour.
- Otherwise, `queryEvents(since, now)` and take the last `ACTIVITY_RESUMED` that passes both filters:
  - its package is not `context.packageName`. Parem has a launch intent, so without this filter its own resume, inside the window, would read as "unmarked app" and flash home colour before the marked app's resume lands.
  - its package has a launch intent in Parem's user (`getLaunchIntentForPackage`, cached per session). Others (permission controller, recents, SystemUI) are ignored, so a permission dialog doesn't flash colour.
- No qualifying event: keep the current `APP_FG`.
- Qualifying event and `marked(pkg) != APP_FG`: write it and `reconcile`.

### Launch trigger (no flash)

In `MainViewModel.startApp`, *after* `startMainActivity` returns without throwing, **and only if `appModeReady`**, set `APP_FG = true` for a marked package and `reconcile`. A failed launch never greys home, and a closed gate never greys anything. This covers slots, folders, gesture letters, swipe apps, clock/calendar (`HomeSlotsController.launchApp`), drawer and omnibox. Websites and double-tap OPEN_APP (`DoubleTapActionManager` bypasses `selectedApp`) are left to the watcher (≤1 s of colour).

### Home

`MainActivity.onResume` stops the watcher, sets `APP_FG = false`, then runs WP5's existing `reconcile`.

- **Why `onResume`, not `onStart`:** if the marked app's launch activity is translucent or a dialog, or finishes at once (trampoline, splash-and-finish), Parem is only paused, never stopped. Coming back then runs `onResume` without `onStart`, and an `onStart` reset would leave home grey. `onResume` follows every `onStart`, so it covers both.
- **Why not `HomeFragment.onResume`:** the drawer's `popBackStack` resumes `HomeFragment` mid-launch (WP5 trap). `MainActivity` is already resumed during that pop, so its `onResume` does not run then and the trap does not apply to it.
- Parem's own dialogs and bottom sheets are windows in the same activity and do not pause it. A system permission dialog over Parem does pause and resume it; resetting to colour while Parem is in front is correct anyway.
- WP5's limit-override clearing stays in `onStart`. Only the WP21 reset moves to `onResume`.

### Marking an app

The "Grayscale" toggle in the app menu walks the user through the gate, one step per tap, in order:

1. No grant → WP5's grant sheet (as in WP5).
2. Grant, no usage access → a dialog: "Per-app grayscale needs usage access to notice when you switch apps." Positive button opens `Settings.ACTION_USAGE_ACCESS_SETTINGS`, the same way `MainActivity` already does for screen time.
3. Grant and usage access, Parem not default home → a dialog: "Per-app grayscale needs Parem as your default home screen to bring colour back." Positive button calls `viewModel.resetLauncherLiveData.call()`, the existing "Set as default launcher" path.
4. Gate open → toggle the mark.

The app is marked only at step 4. When the user comes back from a settings screen, they tap "Grayscale" again. That costs a tap per missing condition, and it avoids a pending-mark state that would have to survive leaving Parem. Unmarking never checks the gate.

The two dialogs follow the existing `Constants.Dialog` pattern: two new values handled in `MainActivity`'s `showDialog` observer, next to `DIGITAL_WELLBEING`. The menus post to `viewModel.showDialog`, so the adapter needs no `Activity`.

### WP5 interaction

`GrayscalePolicy.desired(…)` gains `appForeground`, ORed with manual/focus/limit. `plan()` is unchanged. Color correction turned off inside a marked app is WP5's `UserOverride`, suppressed until the next unmarked app or home. Manual "Now" keeps grey everywhere. Focus-blocked apps never launch.

## Exact scope

- `helper/GrayscalePolicy.kt`: the `appForeground` input, plus `isMarked(csv, pkg)` and `toggle(csv, pkg)`.
- `helper/GrayscaleController.kt`:
  - `appModeReady(ctx)`: grant && usage access && `isParemDefault`
  - `setAppForeground(ctx, Boolean)`
  - `startAppWatch(sinceMs)` and `stopAppWatch()`: a main-looper `Handler`; the query runs on it because it is a single small binder call
- `MainActivity`:
  - `onPause`: record the pause time.
  - `onStop`: start the watch from the pause time. Gate: `appModeReady` and any app marked.
  - `onResume`: stop the watch, `setAppForeground(false)`.
  - `showDialog` observer: the two gate dialogs.
- `Constants.Dialog`: `GRAYSCALE_USAGE_ACCESS`, `GRAYSCALE_DEFAULT_HOME`.
- `MainViewModel.startApp`: the launch trigger, gated on `appModeReady`.
- App menus: a "Grayscale" toggle next to mindful pause in `AppDrawerAdapter` and `HomeSlotsController.showHomeSlotMenu`, routing as in "Marking an app". It is hidden on private rows (same rule as "time limit").
- Prefs: `GRAYSCALE_APPS` (CSV, exported, stored like `MINDFUL_PAUSE_APPS`). `GRAYSCALE_APP_FG` goes in `exportExcludeKeys`.
- Strings (`translatable="false"`): `grayscale_app_on`, `grayscale_app_off`, `grayscale_app_needs_usage`, `grayscale_app_needs_default`. A CHANGELOG line.

## Done criteria

- A marked app is grey from every Parem route. The drawer route does not flicker during the pop.
- Recents marked→unmarked turns colour within about 1 s, and unmarked→marked turns grey.
- A notification tapped from home into a marked app turns grey.
- Home gives colour, and a failed launch leaves home in colour.
- A marked app whose launch activity is translucent or finishes at once: back on home is colour.
- With Parem not the default home, launching a marked app from Parem (opened via its icon) leaves the phone in colour, and so does pressing Home afterwards.
- The toggle routes, in order, to the grant sheet, the usage-access dialog and the default-home dialog, and marks the app only once all three are in place. Each dialog shows its one line and opens the right settings screen.
- With usage access revoked after marking, a marked app launches in colour and nothing stays grey.
- WP5's done criteria still hold with marked apps present.
- Battery measured and recorded in the PR (Test plan).
- `testDebugUnitTest`, `compileDebugKotlin` and `assembleDebug` exit 0.

## Risks & traps

**Never stuck grey:**
- *Gate closed (no grant, no usage access, or another default launcher):* `APP_FG` is never set, so there is nothing to undo.
- *Crash or process death in a marked app:* grey stays, which is correct for that app. A switch to an unmarked app before going home stays grey until the next home press, when `onResume` runs `reconcile`. Accepted gap.
- *Uninstall / force-stop / usage access revoked:* done from Settings or Play, which are launchable and unmarked, so colour returns first. Edges: `adb uninstall`, marking Settings itself.
- *`WRITE_SECURE_SETTINGS` revoked:* WP5's `SecurityException` path. The escape hatch is the system Color correction.
- *Default launcher changed:* happens in Settings (colour); the watcher never restarts, and the closed gate stops the launch trigger if Parem is opened later from its icon.
- *Reboot:* the daltonizer value persists. Parem starts as home, `onResume` runs, and colour is restored.

**Other traps:**
- **Hot files:** `MainActivity.onStart`/`onResume`/`onStop` and `HomeSlotsController` are shared with WP5 and M4-WP2.
- **Work profile and Private Space:** `queryEvents` and `getLaunchIntentForPackage` see Parem's own user only. A recents switch from a marked app into a work-profile or private-space app finds no qualifying event, so it stays grey until the next home press. Accepted gap, same shape as the crash case. `LauncherApps.getActivityList` across profiles would fix the launch-intent filter, but it cannot help if the resume event itself is never in Parem's event stream, so it is not worth the code until the device pass shows which one is missing.
- **Play:** no new permission; disclose this `PACKAGE_USAGE_STATS` use in the listing.
- **Launcher-killing OEMs:** same gap as crash; B only if the device pass shows it.

## Test plan

**JVM:**
- the `desired` truth table with `appForeground`
- `isMarked`/`toggle`
- `UserOverride` while `appForeground` is true, then `ClearSuppression` once it falls

The gate, the tick filter and `since` handling are thin Android glue around `UsageEvents`; they are covered on device, not mocked.

**Device (Pixel, Android 14+; one Samsung or Xiaomi):**
- every done criterion
- a permission dialog inside a marked app causes no flash
- launching a marked app from home causes no colour flash on the first tick (Parem's own resume is filtered out)
- screen off/on mid-session
- `am kill` mid-session
- frozen check: tick log continues for 10 min in another app
- work-profile switch from a marked app: confirm whether the resume event appears in Parem's `queryEvents` at all

**Battery:**
- `dumpsys batterystats --reset`, 30 min screen-on in a marked app vs nothing marked; flag a Parem CPU delta above 1% of device CPU

## Not verified

- that the home process is never frozen on Android 15/16 or by OEM freezers (AOSP constants only)
- how quickly `queryEvents` sees a resume (assumed under 1 s)
- that the next app's `ACTIVITY_RESUMED` timestamp always falls after Parem's `onPause` wall-clock time (AOSP pauses before resuming the next activity)
- whether events from a work profile or Private Space appear in the main user's `queryEvents`
- whether Play reviewers question `PACKAGE_USAGE_STATS` used for this

## Review notes (revision 2)

- **Stuck grey when Parem is not the default home** and **launch trigger not gated like the watcher** (two findings, same fix): accepted. Both the launch trigger and the watcher start now check `appModeReady` (grant, usage access, default home). With the gate closed, `APP_FG` is never written.
- **Toggle UX doesn't say what the feature needs:** accepted. The toggle walks grant → usage access → default home, one line of copy for each, and marks only when all three are in place. This was added to Exact scope, strings and Done criteria. I picked "tap again after each step" over a pending mark that completes on return, because a pending mark would need state that survives leaving Parem. WP5 has that kind of auto-complete for the grant, but it polls while Parem stays in front, and that doesn't apply here.
- **WP5 not on origin:** accepted. The header now says WP21 waits for WP5 to merge and must re-check `desired()`/`plan()` and the `MainActivity` hooks after rebasing.
- **Home stays grey when Parem is only paused:** accepted. The reset moved to `MainActivity.onResume`. WP5's limit-override clearing stays in `onStart`.
- **Tick `since` and own package:** accepted in part. Parem's package is excluded, and "no qualifying event" keeps the current state. **Disagreement on `since` = onStop time:** the next app resumes *before* Parem's `onStop`, so a window starting at `onStop` would miss the resume of an app opened from a notification on home, and that app would stay colour. That breaks a done criterion. `since` starts at the last `onPause` time instead and advances to the last event read. Excluding Parem's package removes the flash the finding was about, even with the earlier start.
- **Work profile / Private Space and the M4-WP20 dependency:** listed as an accepted gap with a device check, instead of switching to `LauncherApps.getActivityList`. The likelier blocker is that `queryEvents` is per-user, so the event never arrives at all; the header now says M4-WP20 is not a hard dependency.

# M4-WP18 — Lock without the accessibility service

## Problem

On API 28+ locking needs `MyAccessibilityService` (Trap #1). It is dead when:
- Android 17 Advanced Protection revokes it (launchers aren't accessibility tools).
- Restricted settings on sideloaded installs.
- The user declined M2-WP5's consent.

M4-WP8 explains this but can't lock.

Parem already ships a device admin: `listener/DeviceAdmin`, `res/xml/policies.xml` (`force-lock`), `MainActivity.enableAdminLauncher`, the pre-P `lockNow()` branch (M4-WP20 would delete it).

## Options

**A. Device admin `lockNow()` as an opt-in fallback.**
- Cost (verified): "After this method is called, the device must be unlocked using strong authentication (PIN, pattern, or password)" ([DevicePolicyManager.lockNow](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#lockNow())). Every gesture lock skips biometrics next unlock.
- With no lock screen set it only turns the screen off (fine).
- `USES_POLICY_FORCE_LOCK` stays available for consumer apps ([device admin deprecation](https://developers.google.com/android/work/device-admin-deprecation)).
- The user must deactivate the admin before they can uninstall Parem ([device admin overview](https://developer.android.com/work/device-admin)).
- Since Android 15, device admin is also behind restricted settings for sideloaded installs ([Android 15 CDD §9.8](https://source.android.com/docs/compatibility/15/android-15-cdd)).

**B. Another public API.** None exists.
- `GLOBAL_ACTION_LOCK_SCREEN` needs accessibility.
- `MANAGE_DEVICE_POLICY_LOCK` is `internal|role` ([Manifest.permission](https://developer.android.com/reference/android/Manifest.permission#MANAGE_DEVICE_POLICY_LOCK)).
- A `WRITE_SETTINGS` short-timeout hack isn't a lock and can strand the user's timeout.

**C. Explain only.** M4-WP8 already does this. Free, but the default double-tap stays broken under Advanced Protection.

## Recommendation

A, offered as a fallback and never as the default. When both methods are available, accessibility wins because it keeps biometric unlock. No new pref: the method follows live state, so nothing to export or go stale.

The tradeoff is disclosed twice before anything is enabled:
- In the option label in Parem's sheets and settings row.
- In `EXTRA_ADD_EXPLANATION`, which the system activation screen shows next to its explicit "Activate" button.

### Where the fallback is offered

| Surface | Admin option? | Why |
|---|---|---|
| Home, first-time `CONSENT` (fresh-install double-tap) | **No** | Most users have a working service. A Calm-phone first impression must not put a PIN-forcing, uninstall-gating option next to "Agree and open settings" for everyone. |
| Home, `EXPLAIN_OFF` (service worked, Android removed it) | Yes | This is the Advanced Protection case: the user chose lock and Android took it away. |
| Home, `OFF_EXPLAINED` toast | Points to it | The toast names Settings › Gestures, where the row below is. |
| Settings, consent sheet after picking Lock screen | Yes | A deliberate re-pick. This is where a user who declined on home goes to get lock back (decline set the gesture to NONE). |
| Settings, Gestures card row | Yes | The one permanent entry point (see below). |

So "user declined" is served through settings, not by showing the admin option to every new install.

## Exact scope

- **`helper/LockServiceCheck.kt`**
  - Add `adminActive: Boolean` to `decide()` (five inputs).
  - New outcome `LOCK_ADMIN`.
  - Order: `enabled && bound` → `LOCK`; `adminActive` → `LOCK_ADMIN`; then the existing order unchanged. `enabled && !bound` with the admin active is `LOCK_ADMIN`, so the silent-swallow case never reaches `performClick`.
- **`ui/home/HomeGesturesController.lockPhone()`**
  - Pass `adminActive = deviceManager.isAdminActive(ComponentName(context, DeviceAdmin::class.java))`.
  - The P+ `when` gets `LOCK, LOCK_ADMIN -> Unit` (both fall through). Hoist the decision into a local so the `try` can see it:
    ```kotlin
    var useAdmin = Build.VERSION.SDK_INT < Build.VERSION_CODES.P
    if (!useAdmin) { val outcome = decide(...); when (outcome) { ... }; useAdmin = outcome == LOCK_ADMIN }
    try {
        if (useAdmin) deviceManager.lockNow() else binding.lock.performClick()
    } catch (e: SecurityException) { /* existing handler, unchanged */ }
    ```
    `LOCK_ADMIN` calls `lockNow()` inside the same `try` and never reaches `performClick()`. A `SecurityException` (admin removed between the check and the call) goes to the existing handler.
  - `CONSENT`: unchanged, no admin option.
  - `EXPLAIN_OFF`: `showLockServiceOff(context, onAccept = …, onUseAdmin = { requestLockAdmin(activity) {} })`. A cancelled activation leaves the gesture as it is, like any other dismissal of this sheet (WP8: the user chose lock, Android undid it).
- **`ui/LockConsentSheet.kt`**
  - `showLockConsent` and `showLockServiceOff` take an optional `onUseAdmin: (() -> Unit)? = null`.
  - When it isn't null, add a third option with `R.string.lock_admin_option`, between accept and the dimmed decline.
  - In `showLockConsent`, `decided = true` before calling it, so the post-dismiss listener doesn't also run `onDecline`.
- **Admin launch helper**
  - Add `requestLockAdmin(activity: MainActivity, onResult: (Boolean) -> Unit)` in `LockConsentSheet.kt`. It builds the `ACTION_ADD_DEVICE_ADMIN` intent (component + `EXTRA_ADD_EXPLANATION` = `admin_permission_message`), sets `activity.onAdminResult = onResult` and launches `enableAdminLauncher`.
  - The pre-P `else` branch of `GesturesSettingsCard.ensureLockPermission` moves into a `requestLockAdmin(activity) {}` call. Pre-P behaviour is unchanged, and WP20 deletes that branch anyway.
- **`MainActivity`**
  - Add `var onAdminResult: ((Boolean) -> Unit)? = null`, following the existing `onWidgetConfigureResult` pattern.
  - In `enableAdminLauncher`, invoke it with `resultCode == RESULT_OK` and then clear it. The existing `prefs.lockModeOn = true` line stays where it is, untouched (see Review notes).
- **`ui/settings/GesturesSettingsCard.kt`**
  - `ensureLockPermission` on P+:
    - Return early when `isAccessServiceEnabled(context) || deviceManager.isAdminActive(componentName)`. With the admin active, picking Lock screen shows no sheet and keeps the gesture.
    - Otherwise call `showLockConsent(onAccept = open accessibility settings, onDecline = onDecline, onUseAdmin = { requestLockAdmin(activity) { ok -> if (!ok) onDecline() } })`. A cancelled activation here reverts exactly like "Not now" (`revertedLockAction`).
  - New row `lockMethod`, in both `layout/` and `layout-land/` `fragment_settings.xml`, below the double-tap / swipe rows. `populateLockMethod()` sets it on P+ only:
    - Admin active: `lock_admin_on_row` → `removeActiveAdmin(…)`, then repopulate.
    - Admin inactive, service not enabled, and any of double-tap / swipe left / swipe right is `LOCK_SCREEN`: `lock_admin_off_row` → `requestLockAdmin(activity) { populateLockMethod() }`. Cancel changes nothing: the gesture was already stored before the tap.
    - Otherwise hidden.
    - Called from `bind()`, after each picker choice and after each admin result. Accessibility state changed in system settings shows up the next time Settings opens (there is no `onResume` hook in `SettingsFragment` today; not adding one).
- **Strings** (`translatable="false"` like the other lock strings until WP9):
  - `lock_admin_option`: "Lock with device admin instead (needs PIN after every lock)".
  - `lock_admin_off_row`: "Lock without accessibility (PIN after every lock)".
  - `lock_admin_on_row`: "Lock uses device admin (PIN after each lock): turn off".
  - Rewrite `lock_service_off_toast`: "Can't lock: accessibility is off. Other options in Settings › Gestures".
  - Rewrite `admin_permission_message`: PIN tradeoff, force-lock only, no data, turn it off in Parem's settings before uninstalling.
- **Manifest and `policies.xml`**: unchanged.
- **`docs/RELEASE_CHECKLIST.md` §2**: replace the stale line "With the service off, double tap falls back to device-admin lock, or toasts and opens settings" (pre-P / pre-WP8 behaviour) with:
  - `- [ ] Service off, device admin on: double tap locks, next unlock asks for PIN (fingerprint refused)`
  - `- [ ] Gestures "turn off" row deactivates the admin; uninstall then needs no extra step`
  - `- [ ] With the admin active, uninstall is blocked until it is turned off, and the system screen says why`
  - `- [ ] Service off, admin off: first explanation offers the admin option, later taps toast and point to Settings › Gestures`
- **Play listing**: `fastlane/metadata/android/en-US/full_description.txt` gets one sentence after the accessibility line: "<b>Device admin:</b> optional fallback for lock when accessibility is unavailable. Uses only the force-lock policy, collects nothing; your next unlock needs your PIN. Turn it off in Settings before uninstalling." Reviewers see device-admin apps with suspicion, and a listing that is silent about it looks like hiding.
- **M4-WP20 coordination:** WP20 must keep `DeviceAdmin`, `policies.xml`, `enableAdminLauncher` and `admin_permission_message`, and delete only the `SDK_INT < P` branches (`useAdmin`'s initial value becomes `false`; the pre-P `requestLockAdmin` call goes).
- **CHANGELOG** `[Unreleased]` entry.

## Done criteria

- With the service off and the admin active, a double-tap or lock swipe locks, and the next unlock asks for PIN/pattern/password.
- With the service bound, locking uses accessibility even if the admin is active.
- With the service enabled but not bound and the admin active, the gesture locks via the admin (no silent swallow).
- Tradeoff text shows before the system "Activate" button.
- The home first-time `CONSENT` sheet has no admin option. `EXPLAIN_OFF` and the settings consent sheet do.
- In settings, with the admin active and the service off, picking Lock screen shows no sheet and keeps the gesture.
- Cancel from the settings consent sheet's admin option reverts like "Not now". Cancel from `EXPLAIN_OFF` or from the settings row leaves the gesture as it was.
- The `OFF_EXPLAINED` toast names Settings › Gestures, and that card shows the "Lock without accessibility" row while a lock gesture is set and neither method is live.
- The settings "turn off" row deactivates; then uninstall needs no extra step.
- `LockServiceCheckTest` has the cases listed in the test plan. RELEASE_CHECKLIST and the fastlane listing are updated. All AGENTS.md checks pass.

## Risks & traps

- Trap #1 is unchanged. The invisible lock view stays.
- The PIN cost sits in the option label, not body text, so users tie it to Parem.
- Play policy: no device-admin-specific rule was found. Device and Network Abuse forbids interfering with the device, so never block uninstall and never request more than `force-lock`. The listing mentions it (above). The privacy policy (M2-WP3, Patric's owner task) needs the same one line; the M2-WP5 Console declaration is about accessibility only and is not changed.
- Admin deactivated in system settings → `decide` falls back to the WP8 flow.
- Restricted settings also gate the admin on 15+; the existing restricted-settings line covers it.
- **Activations made under the old disclosure.** The method follows live state, so an admin activated on Android 7/8 under the old `admin_permission_message`, on a device later updated to 9+, becomes a PIN-forcing lock path the moment the service drops, without the user having seen the new text. Accepted: it needs a pre-P activation plus an OTA, it is rarer still once minSdk is 29 (WP20), and the settings row makes the active admin visible and one tap to turn off.
- **Advanced Protection on before install.** The service never connects, so home stays on `CONSENT` (no admin option) until the user declines. They then reach the fallback by re-picking Lock screen in settings, or through the row if they accepted. Accepted to keep the first-run sheet calm. If device testing shows this is common, the follow-up is gating the `CONSENT` option on `AdvancedProtectionManager` (API 36+, needs `QUERY_ADVANCED_PROTECTION_MODE`; not verified).
- `isAccessServiceEnabled` (enabled, not bound) is what settings checks, so an enabled-but-unbound service hides the row and skips the settings sheet. That is WP8's existing behaviour; the home path still handles it through `decide`.

## Test plan

- **JVM `LockServiceCheckTest`.** Keep the existing cases (all with `adminActive = false`), and add:
  - `adminActive = true`, `enabled && bound` → `LOCK`.
  - `adminActive = true`, `enabled && !bound` → `LOCK_ADMIN`.
  - `adminActive = true` with each former `CONSENT` input (`!connectedBefore`), `EXPLAIN_OFF` input (`connectedBefore && !offExplained`) and `OFF_EXPLAINED` input (`connectedBefore && offExplained`), service off → `LOCK_ADMIN`.
- **Emulator (API 35/36):**
  - Set a PIN and enrol a fingerprint (`adb -e emu finger touch 1`).
  - Admin on, service off: double-tap; fingerprint refused, PIN required.
  - Settings: admin on, service off, pick Lock screen → no sheet, gesture kept.
  - Settings consent → admin option → cancel → gesture reverts; `EXPLAIN_OFF` → admin option → cancel → gesture kept.
  - `OFF_EXPLAINED` toast text; settings row appears; row → activate → lock works.
  - Deactivation row, uninstall with admin active.
- **Device (Patric):**
  - Android 17 with Advanced Protection on: confirm the service gets revoked, the admin can be activated, and lock works.
  - Sideloaded GitHub APK on 15+: the restricted-settings flow for the admin.
  - One OEM skin (Samsung) for the deactivate-before-uninstall UI.

## Not verified

- That Advanced Protection revokes Parem's service. Official docs only document `AdvancedProtectionManager` ([AAPM guide](https://developer.android.com/privacy-and-security/advanced-protection-mode)). The revocation rule itself is sourced from press coverage of Android 17 ([The Hacker News](https://thehackernews.com/2026/10/android-17-advanced-protection-locks.html), [Android Authority](https://www.androidauthority.com/android-17-beta-2-advanced-protection-mode-accessibility-apps-3648860/)).
- That Advanced Protection leaves device-admin activation alone.
- That strong auth is required for the next unlock only (the AOSP behaviour) and not for longer.
- That Smart Lock / trust agents are also skipped.
- No Play Console declaration for a `force-lock`-only admin.
- The exact uninstall UI when an admin is active, per OEM.

## Review notes

- **Settings path / admin check (two findings, one fix):** taken. `ensureLockPermission` returns early when the admin is active; its sheet passes `onUseAdmin` with cancel → `onDecline`; the pre-P branch is what moves into `requestLockAdmin`.
- **Discoverability:** both a row and a toast pointer, not one. The row is the entry point; the toast is what the user sees at the moment of failure, and a row nobody is told about is the same problem again. One string rewrite costs nothing.
- **Admin option on first-time `CONSENT`:** removed (see "Where the fallback is offered"). The "user declined" target is met through the settings re-pick, which is also where a declined user lands, because decline sets NONE.
- **Home cancel semantics:** moot for `CONSENT` now. `EXPLAIN_OFF` cancel keeps `LOCK_SCREEN` stored. That does not conflict with `revertedLockAction`: that rule covers a user *declining their own pick*. `EXPLAIN_OFF` is WP8's "Android undid the user's choice" case, which already keeps the gesture on dismiss so it can explain and point to the fix (now the toast and row).
- **`lockModeOn`:** left untouched in `enableAdminLauncher` and not used by the new callback. It is write-only on origin/next (written in `MainActivity`, `MyAccessibilityService`, `HomeGesturesController`, never read). Flagged as a smell. Deleting it is a separate one-line cleanup, outside this WP, and it should check that export/import doesn't carry the key.
- **Test arithmetic:** fixed (five inputs, explicit cases).
- **Release/Play:** checklist lines and the listing sentence are in Exact scope. The privacy-policy line is noted for M2-WP3.
